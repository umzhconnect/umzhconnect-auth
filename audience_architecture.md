# Audience claim architecture

**Date:** 2026-06-17
**Status:** Implemented — D1-via-YAML stop-gap; D3 migration path documented

---

## Summary

Production tokens must carry `aud` = the target FHIR server base URL (IG requirement, RFC 7519 §4.1.3). Per-audience scope enforcement is required at the AS level.

Chosen approach: **D1-via-YAML** — one Keycloak client per (org, app, target-FHIR-server) triple, generated by Terraform from YAML config files. This is a stop-gap until Keycloak implements RFC 8707 resource indicators (tracked for KC 26.8.0+).

L1 (`client_secret`) is **banned from production**. All clients are L2 (`private_key_jwt`).

---

## Why not D2 (named aud scopes) for this use case

D2 keeps one KC client per org and uses optional `aud:<key>` scopes to select the audience. It cannot enforce at the AS level that a given audience scope is only valid alongside a specific SMART scope set — the AS grants any scope the client has, regardless of which `aud:` scope is also requested. Per-audience scope enforcement requires separate KC clients (D1).

---

## Scale

At 20 hospitals × 5 apps, worst case:  
100 org-apps × 19 target FHIR servers = **~1 900 KC clients**

Keycloak handles this without performance concern. Token issuance (`client_credentials`) is a single indexed DB lookup by `client_id`; client count does not affect latency. All KC objects are Terraform-managed — operators never browse the KC admin console.

---

## Directory layout

```
keycloak/
  config/
    fhir-servers.yaml          # network FHIR server registry (audience key → URL)
    clients/
      hospital-p.yaml          # one file per hospital — Terraform generates N KC clients
      hospital-f.yaml
  terraform/
    audiences.tf               # reads fhir-servers.yaml → aud: scopes + audience mappers
    clients.tf                 # reads config/clients/*.yaml → KC clients + mappers
    scopes.tf                  # SMART system scope definitions (stable, stays HCL)
    realm.tf
    variables.tf
    versions.tf
```

## YAML schemas

### `config/fhir-servers.yaml`

```yaml
# Each key becomes a Keycloak client scope named aud:<key>.
# The audience mapper on that scope sets aud = url in every token issued
# to a KC client that has this scope as a default scope.
servers:
  fhir-hospitalp:
    url: "https://fhir.hospitalp.example"
    description: "HospitalP FHIR server"
  fhir-hospitalf:
    url: "https://fhir.hospitalf.example"
    description: "HospitalF FHIR server"
```

Adding a new hospital's FHIR server = one new entry here.

### `config/clients/<hospital>.yaml`

```yaml
org_id: "hospital-f"
display_name: "HospitalF"
role: "fulfiller"         # realm role assigned to service accounts
tenant: "fulfiller"       # tenant claim (sandbox routing hint — confirm with UMZH)
org_reference: "https://fhir.hospitalf.example/fhir/Organization/HospitalF"

apps:
  # One KC client is generated per (app, audience) entry.
  # KC client_id: {org_id}--{app_id}--{server_key}
  # e.g. hospital-f--ris--fhir-hospitalp
  ris:
    display_name: "RIS System"
    jwks_url: "https://hospitalf.example/.well-known/jwks/ris.json"
    audiences:
      fhir-hospitalp:
        scopes:
          - "system/ServiceRequest.r"
          - "system/Patient.r"
  his:
    display_name: "HIS System"
    jwks_url: "https://hospitalf.example/.well-known/jwks/his.json"
    audiences:
      fhir-hospitalp:
        scopes:
          - "system/Task.cru"
          - "system/Patient.r"
      fhir-hospitalf:
        scopes:
          - "system/Task.cru"
          - "system/Patient.r"
          - "system/Condition.r"
```

**Nothing in YAML is secret.** JWKS URLs are publicly reachable HTTPS endpoints (Keycloak fetches public keys from them). `org_reference` is a canonical FHIR URL, not a credential.

### KC client naming

`{org_id}--{app_id}--{server_key}` — double-dash separator is unambiguous (KC client IDs allow `--`). Example: `hospital-f--ris--fhir-hospitalp`.

## Terraform structure

### `audiences.tf`

Reads `fhir-servers.yaml`. Creates one `keycloak_openid_client_scope` named `aud:<key>` per server, with `include_in_token_scope = false` (suppresses the scope name from the `scope` claim) and an audience mapper that sets `aud = url`.

### `clients.tf`

Flattens the YAML hierarchy (org → apps → audiences) into a map keyed by KC client ID. For each entry:
- One `keycloak_openid_client` with `client-jwt` authenticator and the app's `jwks_url`
- Default scopes = the audience-specific SMART scopes + `aud:<server_key>` (the aud scope is assigned as **default**, not optional — the client has exactly one audience)
- No optional scopes
- Protocol mappers: `org-reference-mapper`, `fhir-context-mapper`, `tenant-mapper`, `realm-roles`

### `scopes.tf`

Defines the full SMART system scope vocabulary (`system/<Resource>.<perms>`) as realm-level KC client scopes. These are stable network-level definitions; clients reference them by name. The `smart-*` user-facing scopes (consent screen, web app) are removed — this is a pure M2M realm.

## Secrets and Vault

The only secret Terraform needs is the Keycloak admin password. No per-client secrets exist in L2.

```
Vault path: secret/umzh-connect/{env}/keycloak
  admin_password: ...
```

Terraform reads it via the HashiCorp Vault provider:

```hcl
provider "vault" {
  address = var.vault_address
}

data "vault_kv_secret_v2" "keycloak" {
  mount = "secret"
  name  = "umzh-connect/${var.environment}/keycloak"
}

provider "keycloak" {
  client_id = "admin-cli"
  username  = var.keycloak_admin_username
  password  = data.vault_kv_secret_v2.keycloak.data["admin_password"]
  url       = var.keycloak_url
}
```

CI/CD authentication to Vault: use JWT/OIDC (no long-lived credentials). The pipeline's OIDC token is the credential; Vault validates it against the CI provider's JWKS.

For local dev, `var.keycloak_admin_password` falls back to a direct variable (set in `.env`, gitignored).

## Onboarding a new hospital

1. Add entry to `config/fhir-servers.yaml` if this hospital's FHIR server is a new audience target.
2. Add `config/clients/<hospital>.yaml` with the org's apps and their per-audience scope sets.
3. `terraform apply`

PR diff: one or two YAML files. The YAML is the audit trail. No HCL changes needed.

## D3 migration path (RFC 8707 resource indicators)

When RFC 8707 support reaches preview in a future Keycloak release (tracked under [keycloak/keycloak#47117](https://github.com/keycloak/keycloak/issues/47117)):

| | D1-via-YAML (now) | D3 (future) |
|---|---|---|
| KC clients | 1 per (org, app, audience) | 1 per (org, app) |
| YAML schema | unchanged | unchanged |
| Token request | `client_id=hospital-f--ris--fhir-hospitalp` | `client_id=hospital-f--ris resource=https://fhir.hospitalp.example` |
| Terraform change | fan-out loop removed; per-client resource allow-list added | yes |
| State migration | `terraform state mv` per client | yes |

The YAML schema is forward-compatible: `audiences` map stays the same; it becomes the per-client allowed-resources list in D3. Operator workflow is unchanged.
