# Audience claim architecture

**Date:** 2026-06-17  
**Updated:** 2026-06-19  
**Status:** Implemented — D1-via-YAML; D3 migration path documented in [ADR 0002](docs/adr/0002-audience-claim-design.md)

---

## Summary

Production tokens must carry `aud` = the target FHIR server base URL (IG requirement, RFC 7519 §4.1.3). Per-audience scope enforcement is required at the AS level.

Chosen approach: **D1-via-YAML** — one Keycloak client per (org, app, target FHIR server), generated by Terraform from YAML config files. See [ADR 0002](docs/adr/0002-audience-claim-design.md) for the full design rationale and evaluation of alternatives.

L1 (`client_secret`) is **banned from production**. All clients are L2 (`private_key_jwt`).

---

## Scale

At 20 hospitals × 5 apps, worst case:  
100 org-apps × 19 target FHIR servers = **~1 900 KC clients**

Keycloak handles this without performance concern. Token issuance (`client_credentials`) is a single indexed DB lookup by `client_id`; client count does not affect latency. All KC objects are Terraform-managed — operators never browse the KC admin console.

## Directory layout

```
keycloak/
  config/
    fhir-servers.yaml          # network FHIR server registry (server key → URL)
    apps/
      hospital-b--lis.yaml     # one file per application — identity + declared scopes
      hospital-b--pharmacy.yaml
      ...
    grants/
      fhir-hospital-a-lab.yaml # one file per FHIR server — access rights granted per caller
      fhir-hospital-b.yaml
      ...
  terraform/
    audiences.tf               # reads fhir-servers.yaml → aud: scopes + audience mappers
    clients.tf                 # reads config/apps/ + config/grants/ → KC clients + mappers
    scopes.tf                  # SMART system scope definitions (stable, stays HCL)
    realm.tf
    variables.tf
    versions.tf
scripts/
  validate-grants.py           # checks grant consistency against app declarations
```

## YAML schemas

### `config/fhir-servers.yaml`

```yaml
# Each key becomes a Keycloak client scope named aud:<key>.
# The audience mapper on that scope sets aud = url in every token issued
# to a KC client that has this scope as a default scope.
# A single organization may operate multiple FHIR servers.
servers:
  fhir-hospital-a-referral:
    url: "https://referral.hospital-a.example/fhir"
    description: "Hospital A — Referral FHIR server"
  fhir-hospital-b:
    url: "https://fhir.hospital-b.example/fhir"
    description: "Hospital B FHIR server"
```

Adding a new FHIR server = one new entry here.

### `config/apps/{org_id}--{app_id}.yaml`

One file per application. Contains identity and authentication config; no audience or scope grants.

```yaml
org_id: "hospital-b"
app_id: "lis"
org_display_name: "Hospital B"
app_display_name: "LIS"
org_reference: "https://fhir.hospital-b.example/fhir/Organization/HospitalB"
role: "fulfiller"
tenant: "fulfiller"
jwks_url: "https://hospital-b.example/.well-known/jwks/lis.json"

# Declared by the app for documentation and validation only — not read by Terraform.
# required_scopes: must be covered by every grant targeting this app (enforced by
#   scripts/validate-grants.py). Represents what the app needs to function at all.
# optional_scopes: what the app can use if granted; may vary per target FHIR server.
required_scopes:
  - "system/Patient.r"

optional_scopes:
  - "system/Observation.r"
  - "system/ServiceRequest.r"
  - "system/Task.cru"
```

**Nothing in the app file is secret.** JWKS URLs are publicly reachable HTTPS endpoints. `org_reference` is a canonical FHIR URL, not a credential.

### `config/grants/{server_key}.yaml`

One file per FHIR server, named after the server key from `fhir-servers.yaml`. Owned by the org operating that server. Drives KC client generation — an app not listed here gets no KC client for this server.

```yaml
fhir_server_key: "fhir-hospital-a-referral"

grants:
  hospital-b--lis:           # app_key = {org_id}--{app_id}, matches apps/ filename
    scopes:
      - "system/Patient.r"
      - "system/ServiceRequest.r"
      - "system/Task.cru"
  hospital-b--pharmacy:
    scopes:
      - "system/Patient.r"
      - "system/MedicationStatement.r"
```

### KC client naming

`{org_id}--{app_id}--{server_key}` — double-dash separator is unambiguous (org/app IDs use single dashes; KC client IDs allow `--`). Example: `hospital-b--lis--fhir-hospital-a-referral`.

## Terraform structure

### `audiences.tf`

Reads `fhir-servers.yaml`. Creates one `keycloak_openid_client_scope` named `aud:<key>` per server, with `include_in_token_scope = false` (suppresses the scope name from the `scope` claim) and an audience mapper that sets `aud = url`.

### `clients.tf`

Loads all app files from `config/apps/` and all grant files from `config/grants/`. Grant files are named after the FHIR server key, so the filename IS the `server_key` — no derivation needed. Flattens the grants into a map keyed by KC client ID. For each entry:

- One `keycloak_openid_client` with `client-jwt` authenticator and the app's `jwks_url`
- Default scopes = the granted SMART scopes + `aud:<server_key>` (audience mapper fires automatically)
- No optional scopes
- Protocol mappers: `org-reference-mapper`, `fhir-context-mapper`, `tenant-mapper`, `realm-roles`

### `scopes.tf`

Defines the full SMART system scope vocabulary (`system/<Resource>.<perms>`) as realm-level KC client scopes. These are stable network-level definitions; clients reference them by name.

## Secrets and Vault

The only secret Terraform needs is the Keycloak admin password. No per-client secrets exist in L2.

```
Vault path: secret/umzh-connect/{env}/keycloak
  admin_password: ...
```

Terraform reads it via the HashiCorp Vault provider:

```hcl
provider "vault" {
  address = var.vault_address
}

data "vault_kv_secret_v2" "keycloak" {
  mount = "secret"
  name  = "umzh-connect/${var.environment}/keycloak"
}

provider "keycloak" {
  client_id = "admin-cli"
  username  = var.keycloak_admin_username
  password  = data.vault_kv_secret_v2.keycloak.data["admin_password"]
  url       = var.keycloak_url
}
```

CI/CD authentication to Vault: use JWT/OIDC (no long-lived credentials). The pipeline's OIDC token is the credential; Vault validates it against the CI provider's JWKS.

For local dev, `var.keycloak_admin_password` falls back to a direct variable (set in `.env`, gitignored).

## Onboarding a new application

1. The calling org adds `config/apps/{org_id}--{app_id}.yaml` with its JWKS URL and declared scopes.
2. Each target org that wants to grant it access adds an entry to the relevant `config/grants/{server_key}.yaml`.
3. Run `scripts/validate-grants.py` to confirm all required scopes are covered.
4. `terraform apply`

PR diff: one app file + one or more grant files. No HCL changes needed.

Onboarding a new FHIR server: add one entry to `config/fhir-servers.yaml`, create `config/grants/{server_key}.yaml`, then `terraform apply`.

## D3 migration path (RFC 8707 resource indicators)

When RFC 8707 support reaches preview in a future Keycloak release (tracked under [keycloak/keycloak#47117](https://github.com/keycloak/keycloak/issues/47117)):

| | D1-via-YAML (now) | D3 (future) |
|---|---|---|
| KC clients | 1 per (app, FHIR server) | 1 per app |
| `config/apps/` | unchanged | unchanged |
| `config/grants/` | drives client generation | becomes per-client resource allow-list |
| Token request | `client_id=hospital-b--lis--fhir-hospital-a-referral` | `client_id=hospital-b--lis resource=https://referral.hospital-a.example/fhir` |
| Terraform change | fan-out loop removed; per-client resource allow-list added | yes |
| State migration | `terraform state mv` per client | yes |
