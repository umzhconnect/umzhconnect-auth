# Realm contract

The realm configuration is the sandbox drop-in contract. Any change here must remain compatible with `umzhconnect-sandbox` unless intentionally diverging (document the reason in [realm-contract.md](realm-contract.md)).

## Fixed realm settings

| Item | Value |
|------|-------|
| Realm | `umzh-connect` |
| Issuer (published) | `http://localhost:8180/realms/umzh-connect` |
| Token lifetime | 300 s |

## Clients

All production clients default to L2 (`private_key_jwt`). L1 (`client_secret`) is not provisioned by default and is banned as a primary/default production client — it is available only as an explicit, per-hospital opt-in **debug client** (`{org_id}--l1`, from `config/hospitals-l1/{org_id}.yaml`). See [ADR 0002](../docs/adr/0002-one-client-per-hospital.md) and [ADR 0004](../docs/adr/0004-reinstate-l1-debug-client.md).

Production clients are generated by Terraform from `config/apps/` + `config/grants/` — there are no hardcoded client IDs. KC client ID format: `{org_id}--{app_id}--{server_key}`. See [config-model.md](config-model.md).

## Mappers (per M2M client)

Applied to both the L2 client (`{org_id}`) and, when provisioned, the L1 debug client (`{org_id}--l1`):

| Mapper | Claim added | Source |
|--------|-------------|--------|
| `client-id-mapper` | `client_id` | Hardcoded to the client's own `client_id` (RFC 9068 §2.2 requires this claim, distinct from `azp`; Keycloak's built-in Client ID mapper is not used because it names the claim `clientId`, not `client_id` — see [keycloak/keycloak#16329](https://github.com/keycloak/keycloak/issues/16329)) |
| `org-reference-mapper` | `extensions.umzhconnect.organization_reference` | Set by AS from the app's `org_reference` field — never by the client |
| `fhir-context-mapper` | `fhirContext` | Reads `authorization_details` from raw request; see [mapper.md](mapper.md) |
| `ecosystem-audience-mapper` | `aud` | Constant ecosystem `aud` — see [ADR 0003](../docs/adr/0003-constant-ecosystem-audience.md) |
| `auth-level-mapper` | `extensions.umzhconnect.auth_level` | Required on every client — hardcoded `"L2"` on the primary client, `"L1"` on the debug client. Reinstated by [ADR 0004](../docs/adr/0004-reinstate-l1-debug-client.md), superseding the deferral in [ADR 0001](../docs/adr/0001-defer-auth-level-claim.md); any future L3 client must stamp `"L3"` the same way — there's no level for which the claim is absent |

`auth_level` stays under `extensions.umzhconnect` rather than moving to a bare top-level claim: that container is reserved for claims specific to the UMZH-Connect authorization model with no external spec defining them (same reason `organization_reference` lives there). `client_id` and `fhirContext` are top-level *because* RFC 9068 and SMART App Launch respectively require/define them there — not UMZH-Connect inventions. `auth_level` has no external spec backing it, so nesting it keeps that line consistent and avoids ever colliding with a future top-level standard claim of the same name. Nothing technical prevents a top-level claim — JWT claims are a flat namespace — this is a convention choice, not a constraint.

## RFC 9068 conformance

Each M2M client sets `"access.token.header.type.rfc9068" = "true"` in `extra_config` (native Keycloak 26.2+ client attribute), so the access token's JWT **header** carries `typ: "at+jwt"` per RFC 9068 §2.1, not the default `"JWT"`. This is separate from — and unrelated to — the `typ: "Bearer"` claim Keycloak places in the token **payload**, which RFC 9068 does not govern and which is left as-is.

## Scopes

Custom client scopes are declared in `config/scopes.yaml` and created by `scopes.tf`. All M2M hospital clients receive the `default_scopes` set automatically; `optional_scopes` are registered but not assigned by default.

Scope names follow the SMART Backend Services convention (`system/{Resource}.{interactions}`). The full list is in [`config/scopes.yaml`](../keycloak/config/scopes.yaml).

## Audience (`aud`) binding

Every M2M client carries a constant `aud` identifying the umzh-connect ecosystem as a whole (the realm issuer URL), via the `ecosystem-audience-mapper` protocol mapper on each client. Target-specific `aud` binding (RFC 8707) is deferred until Keycloak's `resource-indicators` support is non-experimental. There is no per-hospital inbound allow-list — any FHIR server in the realm accepts any token. See [ADR 0003](../docs/adr/0003-constant-ecosystem-audience.md).

## Roles

`admin`.

## Sandbox-only config (gate or remove for production)

- **`users.tf`** — `web-app` PKCE client with ROPC (`direct_access_grants_enabled = true`) and three demo users with hardcoded passwords. Remove or gate behind a flag.
- **`smart-*` scopes** in `scopes.tf` — user-facing consent screen scopes, not M2M. Remove or gate.
- **`ssl_required = "none"`** in `realm.tf:11` — must be `external` or `all` in production.
- **`start-dev`** in `docker-compose.yml` — disables all Keycloak production hardening; dev-only.

## Known divergences from the sandbox `realm-export.json`

| Setting | This repo | Sandbox | Reason |
|---------|-----------|---------|--------|
| `registrationAllowed` | `false` | `true` | No self-registration needed for M2M |
| `displayName` | `"UMZH Connect"` | `"UMZH Connect Sandbox"` | Intentional |
| Built-in scopes (`email`, `profile`, `roles`, …) | Present | Absent from export | Keycloak includes them by default; sandbox export skipped them |
